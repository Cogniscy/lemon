Рабочий каталог: D:/Projects/lemon.

## 1. Цель

Новый пользователь устанавливает пакет, запускает автономный пример и понимает,
что именно измеряет LEMON и где его ограничения. Исследователь может проследить
путь от входных данных и конфигурации до опубликованных результатов.

Критерии успеха:
- wheel устанавливается в чистое окружение, демо работает вне checkout;
- для демо не нужны API-ключи, загрузка моделей, датасеты и LaTeX;
- текстовый scorer и proxy по метаданным представлены как разные методы;
- инструкции соответствуют файлам и командам текущего репозитория;
- происхождение чисел в статье явно указано.

«Автономный» означает без сети во время запуска после установки зависимостей.
Полностью офлайн-установка требует предварительно подготовленного wheelhouse
и не входит в первую итерацию.

## 3. Границы

Первая итерация не меняет формулы, словари факторов и исторические результаты.
Не добавляем Docker, сервис, веб-интерфейс и новые модели.
Не исправляем семантические ограничения локальными исключениями под демо.
Не выбираем лицензию за правообладателя и не придумываем экспертные данные.
Архивирование документации не должно ломать существующие ссылки.
Исследовательские скрипты могут требовать checkout; базовый CLI — нет.

### A2. CLI и автономное демо

Добавить:

Команды:
    python -m lemon_factor --help
    python -m lemon_factor demo
    python -m lemon_factor demo --format json

Контракт:
- argparse, без новой runtime-зависимости;
- демо использует существующий score_predicate_decomposition;
- ресурсы загружаются через importlib.resources, без зависимости от cwd;
- stdout содержит результат, stderr — ошибки;
- выход 0 при успешном расчёте, 2 при ошибке аргументов;
- никаких файлов на диске по умолчанию;
- случаи: правильный факт, отсутствующая relation cue, отрицание,
  отношение к другому участнику;
- известные ложноположительные ответы показаны как ограничения;
- никаких заранее вписанных оценок вместо реального вызова scorer.

JSON v1:
- schema_version, method, package_version;
- cases: id, source_edge, text, score, components, known_limitation;
- components используют существующие factor, role, weight, covered,
  score, evidence_type, evidence;
- method = lexical_factor_coverage;
- known_limitation — пояснение демонстрационного случая, не прогноз модели.

Не дублировать ресурсный набор между examples и установленным пакетом.

## 7. Порядок реализации и приёмка

A1 -> A2 -> A3 -> A4: первый небольшой законченный пакет изменений.
B1 -> B2: отдельный пакет, поскольку меняется контракт результатов.
C1 -> C2 -> C3: после стабилизации интерфейса и формата отчётов.

Перед первой правкой:
1. повторно проверить git status и применимые AGENTS.md;
2. сохранить перечень исходных локальных изменений;
3. запустить полный baseline pytest без сетевых вызовов;
4. проверить инструменты сборки и доступность временного каталога;
5. проверить актуальные официальные инструкции используемых средств сборки/CI.

Приёмка A:
- успешный clean-install smoke вне checkout на Windows/Linux;
- demo без сети и секретов;
- полный отчёт по тестам, без заявления «всё зелёное» при необъяснённых сбоях;
- README-команды проверены;
- формулы и исторические числовые результаты не изменены.

Приёмка B:
- legacy/new reader покрыты тестами, включая конфликт ключей;
- proxy обозначен во всех затронутых таблицах и графиках;
- выбранный backend не зависит от случайно установленных библиотек.

Приёмка C:
- мини-эксперимент воспроизводится из wheel;
- публикационные результаты имеют карту происхождения и список пробелов;
- документация не содержит ссылок на отсутствующие команды.
